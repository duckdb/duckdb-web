  extended_description: |
    DuckBridge moves whole databases between SQL Server and DuckDB and translates the SQL in between,
    so a team that lives in T-SQL can do its heavy processing in DuckDB and keep SQL Server as the
    system of record.

    Functions:
    - `bridge_import(dsn, ...)`: copy a SQL Server database (tables, views, keys, identity values) into the
      current DuckDB database with parallel key-range streams.
    - `bridge_run(tsql, ...)`: translate a T-SQL script to DuckDB SQL and run it here, with a SQL Server
      compatibility prelude (integer division, NULL ordering, case-insensitive comparisons, UTC).
    - `bridge_export(target, ...)`: push tables to SQL Server (live load with bulk copy, or a restorable
      `.bak` with optional restore verification), to PostgreSQL, to Parquet, or to a T-SQL script.
    - `bridge_transpile(from, to, sql [, target_version])` and `bridge_prelude(nocase)`: the translator
      and the prelude as plain functions. Dialects: `tsql`, `duckdb`, `postgres`.

    SQL Server is reached natively over TDS (no ODBC or `bcp`), with Windows authentication by default
    (`DOMAIN\user`, `user@domain`, or integrated login on Windows) and SQL logins otherwise. Passwords in
    `mssql://` URLs are percent-encoded. The translator is DuckBridge's own; constructs it cannot translate
    are reported, never silently changed. Every table function returns `(object, kind, rows, note)` rows.
    The extension opens a pool of connections to the host database at load time, so `parallel` is capped
    at 64. Source and CLI: https://github.com/singhpratech/duckbridge
