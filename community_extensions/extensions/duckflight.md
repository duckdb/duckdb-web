  extended_description: |
    DuckFlight lets other programs connect to DuckDB and run queries, the way they would with
    a data warehouse. `psql`, JDBC, SQLAlchemy and BI tools connect as if it were PostgreSQL.
    ADBC drivers connect over Arrow Flight SQL, and another DuckDB can attach it as a catalog.

    Clients can query anything that DuckDB can: its own tables, attached databases, Iceberg and
    DuckLake catalogs, and Parquet or CSV files in object storage. Everything runs inside the
    DuckDB process that loaded the extension, so there is nothing else to deploy and no data to
    copy. It works on a laptop, and a
    [Docker image and Helm chart](https://github.com/sidequery/duckflight-extension/blob/main/docs/DOCKER.md)
    are available for running it for a team.

    Clients can connect over four protocols, which can run at the same time:

    | Protocol | Start function | Clients | Credentials |
    | --- | --- | --- | --- |
    | PostgreSQL wire | `duckflight_pg_serve` | `psql`, Psycopg, JDBC, SQLAlchemy, BI tools | Users, OIDC, mTLS |
    | Arrow Flight SQL | `duckflight_flight_serve` | ADBC drivers, DuckDB's Airport extension | Users, bearer tokens, OIDC, mTLS |
    | HTTP (Arrow IPC) | `duckflight_http_serve` | Anything that can `POST` JSON and read Arrow | Bearer tokens, OIDC, mTLS |
    | Quack | `duckflight_quack_serve` | Another DuckDB, through its `quack` extension | Bearer tokens, OIDC, mTLS |

    Every listener requires authentication, and an address other than loopback also requires
    TLS. One `duckflight.toml` file holds users, bearer tokens, OIDC providers, client-certificate
    identities and the TLS certificate. Bearer tokens carry scopes, so a token can be limited to
    reads. On DuckDB 2.0.1, SQL-managed roles can also restrict clients to specific tables,
    columns and rows, with column masks and row filters.

    Functions that start, stop and list listeners:

    | Function | Purpose |
    | --- | --- |
    | `duckflight_pg_serve(address, config_file)` | Starts a PostgreSQL listener and returns its protocol and bound address. |
    | `duckflight_flight_serve(address, config_file)` | Starts an Arrow Flight SQL listener. |
    | `duckflight_http_serve(address, config_file)` | Starts an HTTP listener that returns Arrow IPC. |
    | `duckflight_quack_serve(address, config_file)` | Starts a listener for DuckDB's Quack protocol. |
    | `duckflight_servers()` | Lists running listeners and their bound addresses. |
    | `duckflight_stop(protocol, address)` | Stops a listener and returns its status. |
    | `duckflight_core_status()` | Reports whether the runtime loaded, with a reason when it did not. |

    Functions that create credentials in `duckflight.toml`:

    | Function | Purpose |
    | --- | --- |
    | `duckflight_user_create(config_file, name)` | Adds a user and returns a generated password once. `password_file` supplies your own. |
    | `duckflight_token_create(config_file, name)` | Adds a bearer token and returns it once. `scopes` sets what it may do. |
    | `duckflight_config_check(config_file)` | Validates a config file the way a listener does and reports what it defines. |

    Only the DuckDB process that owns the database can call the serve, stop, list and
    credential functions. A client connected through a listener cannot, whatever its credentials
    allow. Secrets are never function arguments, and the file stores only digests and password
    verifiers.

    DuckFlight runs on Linux and macOS, on amd64 and arm64. See the
    [quickstart](https://github.com/sidequery/duckflight-extension/blob/main/README.md#quickstart),
    [client examples](https://github.com/sidequery/duckflight-extension/blob/main/docs/CLIENTS.md),
    [authentication](https://github.com/sidequery/duckflight-extension/blob/main/docs/AUTHENTICATION.md)
    and [SQL access controls](https://github.com/sidequery/duckflight-extension/blob/main/docs/ACCESS_CONTROL.md).

    The automatically detected functions below also include PostgreSQL compatibility macros,
    such as `to_char` and `quote_ident`, and internal session and catalog helpers. They let
    PostgreSQL queries and client metadata discovery work; they are not a complete
    implementation of PostgreSQL's functions. Their catalog comments describe each one. The
    native functions in the tables above have no catalog descriptions, because the table-function
    C API they use does not provide a way to set them.
