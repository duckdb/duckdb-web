    -- 2. Learn the extension: every command, and where the language help is
    malloy;

    -- 3. The data: TPC-H, generated by DuckDB's tpch extension
    INSTALL tpch;
    LOAD tpch;
    CALL dbgen(sf = 0.01);

    -- 4. Write a model and save it as tpch.malloy (here with COPY, so the
    --    example runs as pasted; Claude writes the file directly)
    COPY (SELECT '
    source: customers is duckdb.table(''customer'') extend {
      primary_key: c_custkey
    }
    source: orders is duckdb.table(''orders'') extend {
      primary_key: o_orderkey
      join_one: customers with o_custkey
      measure:
        order_count is count()
        revenue is o_totalprice.sum()
      view: by_segment is {
        group_by: customers.c_mktsegment
        aggregate: order_count, revenue
        order_by: revenue desc
      }
    }
    ') TO 'tpch.malloy' (FORMAT csv, HEADER false, QUOTE '');

    -- 5. Load it into this connection
    malloy import 'tpch.malloy';

    -- 6. Check what it built
    malloy describe orders;

    -- 7. Answer from the model
    run: orders -> by_segment;

    -- 8. Keep it: install the model in the database, so every connection can
    --    query its sources by name (and later sessions too, in a database file)
    malloy install 'tpch.malloy';

  extended_description: |
    **malloy** gives an AI agent a semantic layer it builds itself and a query
    surface, inside DuckDB.

    Point an agent at the extension and have it run `malloy;`. That lists every
    command, and `malloy help` carries Malloy's language reference, so the agent
    learns Malloy from the extension. Give it your tables and whatever context you
    have (the questions people ask, existing SQL, documentation) and it writes a
    Malloy model: sources, joins, dimensions, measures and views. Later questions
    are answered from that model, so "revenue" or "an order's customer" means the
    same thing in every answer.

    In a cold-start test on TPC-H (sf=1), Claude built a model from the 11
    odd-numbered queries, then answered the 11 even ones without changing it. All
    22 matched the official answers, with no hand-written SQL.

    Malloy aggregates stay correct across joins that fan out, and results can be
    nested.

    - `run:` statements, and `%{ ... }%` for a Malloy query anywhere SQL takes a table
    - a model per connection (`source:`, `query:`, `malloy import 'model.malloy'`),
      or installed in the database for every connection (`malloy install`)
    - `malloy sources`, `malloy describe <source>`: what a model contains, with
      each field's description

    Documentation: https://github.com/lloydtabb/malloy-duckdb
