[Atlan](https://atlan.com/) now runs its entire data platform on DuckDB and object storage, handling both OLAP and OLTP workloads. DuckDB runs in-process on Parquet files in Amazon S3, a DuckDB service on AWS micro-VMs has replaced StarRocks at about 40% lower cost, and Atlan's new AI context layer is built on the same foundation. Several of Atlan's patches are in [DuckDB 2.0]({% post_url 2026-10-21-announcing-duckdb-200 %}).

> Quote It almost seemed too good to be true: in-process, zero external dependencies, lightweight and super fast.
>
> -- Mustafa, machine learning engineer, Atlan

## What Atlan Does

Atlan started as an active metadata platform: a data catalog and lineage tool that pulls metadata from every warehouse, database and BI tool an organization runs, so data teams can see where a number came from, who owns it, and whether it can be trusted. That problem only grows with the organization, which is why Atlan's customer base skews toward large enterprises, including Fortune 100 companies.

The same question now comes from AI agents. When an agent answers "what was our churn rate last quarter?", a 200 OK response from the API does not mean the answer is correct; the agent may not know which source it used. Atlan is positioning itself as a context layer for AI: governed, verifiable context so that an agent's output can be traced and checked in the same way as a dashboard. Gartner does not yet have a category for this, but one is forming, and Atlan is competing in it.

## Processing Metadata on Spark

Building lineage takes a lot of processing. Atlan ingests query history from its customers' warehouses, billions of rows of it, and works out which tables feed which reports. A couple of years ago that ran on [Apache Spark](https://spark.apache.org/).

Spark worked, but it was expensive. Egress and compute costs grew with every customer, and the pipelines regularly failed with out-of-memory errors that engineers had to investigate. The workload was batch analytics over files in object storage, and running a distributed cluster for it added cost and operational work the team wanted to avoid.

## Moving to DuckDB

Atlan had been following DuckDB since the 0.2 releases. For a team that wanted to process files in S3 without running a cluster, it fit well: it runs inside the Python process the pipeline already uses, it has no external dependencies, and it reads Parquet from object storage directly. **"It almost seemed too good to be true,"** says Mustafa, a machine learning engineer who has been at Atlan for four years and led the migration together with an architect.

The early builds crashed with segmentation faults, and the team filed a series of issues in 2024, some of which led to improvements in DuckDB's Parquet reader. The approach still suited Atlan: start with a small component running inside the existing process, and add infrastructure only when a workload needs it.

## How the Pipelines Run Today

Atlan's metadata pipelines now run DuckDB in-process, inside Python workers on Kubernetes pods and [Temporal](https://temporal.io/) workflows. Each worker reads the Parquet files it needs from S3, runs the lineage and processing queries locally, and writes results back to object storage. Atlan does not need to size a cluster, keep a coordinator running, or deploy a second system on a customer's infrastructure. That last point matters because many of its enterprise customers want both the platform and the data to stay in their own cloud account.

Data volumes are the same as before. Across its customer base Atlan processes hundreds of millions of rows on a typical day and billions on the busiest days. According to Mustafa, the pipelines are faster than the Spark versions and cost far less to run.

## Replacing StarRocks and ClickHouse

After the Spark migration, DuckDB became Atlan's default choice for any workload that reads or writes S3, and the company has since replaced other systems with it.

The most recent was [StarRocks](https://www.starrocks.io/). Earlier this year, before DuckDB's major release, Atlan benchmarked the two and StarRocks performed better. The team continued testing, and this month it shut down its StarRocks cluster. It now runs an in-house service based on DuckDB on AWS micro-VMs that reads and writes object storage directly. Costs fell by about 40%.

Atlan is also replacing [ClickHouse](https://clickhouse.com/) for trace storage with a design that writes from DuckDB directly to object storage, mainly because it is easier to deploy. The new AI context layer, built with AWS as primary partner, uses DuckDB to read and write S3, with [Apache Iceberg](https://iceberg.apache.org/) tables and an Iceberg REST catalog on top. Atlan can still be deployed on any cloud, but its data platform now consists of DuckDB and object storage, handling both OLAP and OLTP workloads.

## Contributing to DuckDB 2.0

Atlan is already running the [DuckDB 2.0]({% post_url 2026-10-21-announcing-duckdb-200 %}) alpha internally and plans to ship its next data-platform release on it, having seen no regressions compared with the 1.x release it used before. Mustafa has had several pull requests merged for 2.0: a fix for a class of queries that failed with out-of-memory errors instead of spilling to disk; an option that lets DuckDB's external file cache for object-storage reads spill to disk as well, so that a 100 MB Parquet file is not evicted from the cache as soon as a second file is queried; and a set of JSON functions (in-place modification, semantic diff, set) that came out of Atlan's metadata workloads.

Atlan's next proposals concern its heaviest workload, Iceberg on S3: better manifest fetching and caching, fewer round trips to object storage, and improved filter pushdown in the Iceberg scanner and Parquet reader.
