In 2024, [Hex](https://hex.tech/) rebuilt its compute engine around DuckDB and [Apache Arrow](https://arrow.apache.org/), taking Python out of the data path and cutting project runtimes by roughly 5 to 10 times. That engine now runs underneath Hex's agentic data platform, where AI agents increasingly decide what analysis gets done.

> Quote DuckDB has completely transformed our product. We couldn't have built what we built without DuckDB.
>
> -- Caitlin Colgrove, co-founder and CTO, Hex

## Hex in Brief

[Hex](https://hex.tech/) is an agentic data platform used for self-serve analytics, data apps and dashboards, and for managing the semantic models and context that agents need. It works with whatever warehouses a company already runs, so it needs its own engine for everything that happens after data is pulled in. That engine is DuckDB.

DuckDB's role at Hex has grown in three stages: a bridge between SQL and Python, the core of an engine that took Python out of the data path, and the infrastructure beneath a product where agents do more and more of the analysis.

## Stage One: Bridging SQL and Python

Hex first integrated DuckDB in 2021 to solve one specific problem: letting SQL queries build on each other. At the time, Hex was a data notebook. In older data tools, analysts typically got one query, so they contorted their logic into a single statement that could run to hundreds or thousands of lines.

**"It was really hard to debug,"** Colgrove recalls. Notebooks are popular because they let you work step by step. But to break analysis into a series of SQL queries, each step has to operate on the result of the one before.

That raised an awkward question. Once the first query had run against the data warehouse, its results lived in memory inside Hex, not in the warehouse. **"It's not actually obvious how you would run another query on it,"** she says. The team looked at several options, including operating directly in pandas.

Then they found DuckDB, which could take a pandas DataFrame and query it as if it were a database table. **"We had it stood up within a couple days," Colgrove says. "It all runs locally. It's just a library, so it was incredibly easy for us to use."**

The resulting feature, which Hex launched as Dataframe SQL, became one of Hex's breakout moments. **"It seems so simple,"** says Colgrove, **"but the quality-of-life upgrade that people working with data got from being able to stage their logic into a DAG, rather than all in these big monoliths, was enormous."** For years afterwards, it was one of the "aha" moments Hex pointed new users toward.

In this first stage, DuckDB was a bridge. Hex notebooks ran on a Python kernel, intermediate results lived in pandas DataFrames, and DuckDB let SQL access that Python memory as if it were a database.

## Stage Two: Taking Python out of the Data Path

That role has outgrown the original bridge. Early Hex needed an active Python process to run at all, while the current architecture does not need it. Data inside the platform now moves mostly as [Apache Arrow](https://arrow.apache.org/), with DuckDB doing the transformation work. Python is still there for users who want it, but it is no longer the mandatory layer every piece of data passes through.

Hex documented that shift publicly in September 2024. In a blog post on its new compute engine, engineer Dylan Scott explained that pandas DataFrames had served as the common interchange format between every cell. SQL, charts, pivots, maps and spreadsheets all materialized a DataFrame in the Python kernel's memory, even when no Python touched the data. In some projects, that loading and DataFrame creation took up more than 90% of total runtime.

Hex replaced it with a DuckDB-based architecture. Cells now write their results as Arrow tables to a cache in Amazon S3, and pass around a lightweight stand-in called a LazyDF. DuckDB queries the underlying data in Hex's backend data service, and only final results reach the user. Data is pulled into Python only when a Python cell actually asks for it. Hex called it the most fundamental performance change it had ever made.

The gains are large. Hex reported project runtimes falling by roughly 5 to 10 times, depending on project complexity and data size, with the biggest gains in projects built mainly from SQL and no-code cells.

| Test project | Runtime before | Runtime after |
|------------------------------|----------------|----------------|
| Performance test project | 12 s | 1 s |
| Important internal project | 15–20 s | 3–5 s |
| Critical customer workload | over 2 min | under 30 s |

The rewrite was about more than speed, it also reduced memory pressure, allowing projects more freedom to work with larger datasets. To make it work, Hex converted the backends of all its no-code cells from Python to SQL. Their operations are now written in HexQL, an internal language that Hex translates at runtime into DuckDB SQL or into other SQL dialects, so work can also be pushed down into customer warehouses. Hex said the move freed it from the limits of pandas formats and of the Python runtime itself.

## Why Hex Didn't Build Its Own Database

Colgrove calls it "medium data" scale. Users rarely pull their whole warehouse into Hex; they pull a segment of it and then slice and dice. **"DuckDB works incredibly quickly. It's very performant,"** she says. It powers the filtering and interactivity behind the data apps Hex users build. Users can still export results in formats such as CSV.

The arrangement also lets Hex stay focused on what it is. About a year ago, as the team built out its internal systems, Colgrove turned to an engineer and asked whether they were accidentally building a database. **"We're not a database company. We don't want to be a database company,"** she says. **"That's just not our expertise."** Instead, all Hex-side transformation runs on DuckDB. **"It's hard to overstate how critical it is to the product just working at all."**

## Stage Three: Agents Decide the Work

The architecture Hex built for humans turned out to be exactly what AI agents needed. A Hex notebook is, at its core, a graph of data transformations, with DuckDB executing the steps. That made it powerful before AI. **"It turns out, just like humans like to build things up piece by piece and build upon previous things, agents work that way too,"** Colgrove says.

That changes who drives the analysis. In early Hex, a person decided every step and built every cell by hand. Increasingly, an agent decides which queries to run and which transformations to chain, and DuckDB executes them.

Hex was among the first to ship a full data agent that does real analysis, not just text-to-SQL. Colgrove credits the speed to that substrate: agents can replicate what human analysts do, building an analysis step by step on a real data backend. That backend lets Hex cache results and run work in different places, in the browser or on the server.

The result, she argues, is the power of a classic BI tool such as Tableau, built by an agent. Hex dashboards are now defined as code, so an agent can operate on them, while people can still use point-and-click editing. Underneath sits the context layer: semantic models, markdown files and observability that keep agent output trustworthy.

Agent traffic has not yet strained that engine, but Hex expects it to within about six months. Data agents have trailed coding agents, and data teams have rolled out self-serve analytics cautiously. That is now changing: instead of a hundred people opening Hex directly, a company might have 10,000 employees reaching it through an AI assistant over [MCP](https://modelcontextprotocol.io/). Every one of those queries lands on DuckDB.

## Where Hex Goes Next

> Neither of the two directions below is a shipped feature; both are areas Hex is exploring.

Hex is watching two DuckDB developments closely. The first is the lakehouse. **"If you squint, [Iceberg](https://iceberg.apache.org/) plus DuckDB looks a lot like a data warehouse,"** Colgrove says. Earlier experiments hit rough edges, especially around catalogs, but many Hex customers want exactly this setup. Hex already has a built-in DuckDB connector and already runs DuckDB internally, so it could offer customers an Iceberg-based alternative to expensive warehouses.

The second is client-side execution, something Hex has wanted for a long time. Because the platform no longer depends on a Python process, more analysis could in principle run directly with DuckDB, closer to the user. What it still needs is a client-server protocol to support that.

Hex also runs entirely on AWS, so it welcomed DuckDB Labs joining AWS. **"We have such a great relationship with AWS," Colgrove says, "and them giving you the extra support just felt like it really did match."**

## A Library That Became a Foundation

Hex's DuckDB story runs from a two-day prototype to infrastructure beneath an AI analytics product. It began as a bridge that let SQL read Python's results. It became part of an architecture that freed Hex from Python as a mandatory data layer, without Hex becoming a database company. Now it executes work that agents, more and more, choose for themselves.

Asked how to measure DuckDB's impact, Colgrove struggles to isolate it. **"It's such a core piece of technology that we built on top of,"** she says. **"What do you want to measure? Our whole business?"**
